# 6.1sol 执行方案：签到证据生命周期与 PT 状态归并收敛

## 目标

解决“同一批站点反复显示缺少证据、重复进入待补证”的问题。保留现有 V1 成熟签到流程、账号绑定、Profile、OCR、验证码处理和全部 PT 补签能力；只收敛状态分类、证据生命周期、Harvest 依赖边界和同步验收。

当前生产事实（2026-10-09，Asia/Shanghai）：

- V1 当日 25 项已产生 final 报告：6 signed、2 already_signed、10 not_available、5 needs_attention、2 deferred。
- Harvest 导出 35 个站点全部为 `unknown`，`taskCompletion` 为空；这表示 Harvest 没有可用当日回执，不表示 35 个站点签到失败。
- PT 监测目录有 30 个站点；当前快照为 1 signed、2 already_signed、23 unknown、4 needs_attention。
- 同步任务本身可以成功上传，NAS 面板健康；主要问题是未知状态和历史不明回执被混入当前“待补证”展示。
- `audiences.me`、`piggo.me`、`www.hdkyl.in` 当前只读核验没有得到权威当日信号；不能把它们改成成功，也不能再次提交。

## 不变的安全边界

执行前更正（2026-10-09）：`inLegacyPlan=false` 不等于未授权。精确书签目录内、现有私有 `ptFallbackOnlyEnabled=true` 且执行绑定可验证的单站补签属于已授权执行范围，必须保留。此前将全部监测站点降为仅观测的段落错误，以下按纯观测和已授权单站补签区分。只读预算使用有界幂等 claim 与事件恢复，而不是失败一次就永久停止当日核验。

1. V1 是唯一浏览器执行者，observation 只负责 Harvest 观察、状态归并、调度租约和脱敏发布。
2. Harvest 的 `userId` 不能作为 PT 账号绑定；PT 账号必须来自当前 V1 plan/profile/account binding。
3. Harvest signed/already_signed 只记为 Harvest 来源状态，不触发 V1 重复签到。
4. 注册 PT 的 fallback 必须经过当前账号、当前上海业务日、reviewed passive page 和权威 `not_signed` 证据；证据不完整时禁止提交。
5. `submission_outcome_unknown`、`submissionAttempted=true`、原生意图 pending 均保持只读核验和禁止重放。
6. 站点维护、TLS、DNS、上游 5xx、限频、交互验证属于外部条件；不进入本地失败率，不为它们启动登录循环。
7. 无补签授权、无唯一账号绑定或不在当前精确书签目录的站点只能观测；日常计划之外的现有已授权单站 PT 补签能力保留。
8. 不复制 Cookies、Profile、DPAPI、Token、密码或原始截图；不修改普通 Chrome、账号配置或书签范围。

## 目标状态模型

将“执行状态”和“证据状态”分开。原始 V1/Harvest 回执继续保留，面板使用同一业务日的 `effective` 归并状态。

执行状态只使用：`signed`、`already_signed`、`not_available`、`deferred`、`needs_attention`、`not_started`。

PT 证据状态增加明确原因：

- `confirmed`: 当前日权威 signed/already_signed 证据。
- `guarded_read_needed`: 已绑定、可执行、Harvest 未确认或 unknown，等待一次受控只读核验。
- `not_signed_confirmed`: 当前账号当天权威确认未签到，可授权一次 V1 提交。
- `verification_pending`: 已提交但结果不明，只读核验，禁止重放。
- `monitor_only_unconfirmed`: 纯观测、未授权执行的站点没有回执；不表示失败。已启用且绑定有效的单站补签站点按受控复核状态处理。
- `external_blocked`: 维护、TLS、DNS、上游或交互验证；站点恢复后再按策略复核。
- `unavailable` / `disabled`: 有权威未开放或配置取消证据。

面板必须把 `monitor_only_unconfirmed` 从“待补证/需处理”中分离；`verification_pending` 只显示历史动作审计，不产生新的提交按钮或自动重试计数。

## 分批实施

### P0：先修状态归并，不改变签到动作

涉及：

- `observation/src/pt-status.mjs`
- `observation/src/bridge.mjs`
- `observation/public/dashboard-model.mjs`
- `observation/public/overview-model.mjs`
- 相关 schema、pt-status 文档和测试

要求：

1. 归并优先级固定为：同日权威 execution supplement > 同日权威 V1 > 同日权威 Harvest > 非权威/历史/未知。
2. 旧 `submission_outcome_unknown` 必须保留在 `observations`/ledger 中，但如果同日已有绑定的权威 passive completion，`effective` 显示完成并标记 `reconciledFromUnknown=true`。
3. Harvest `unknown` 且没有 task completion 时，日常 PT 与具备安全只读能力的已授权单站 PT 标为 `guarded_read_needed`；未授权纯观测站点标为 `monitor_only_unconfirmed`。
4. 统计增加 `monitorOnlyUnconfirmed`、`verificationPending`、`externalBlocked`，并验证成功率分母不包含 externalBlocked、disabled、monitorOnlyUnconfirmed。
5. 所有日期计算使用 `Asia/Shanghai`；昨天的证据只能进入历史日历，不能充当今天回执。

P0 验收：同一 fixture 同时包含 Harvest unknown、旧 V1 unknown、同日 execution signed、非注册监测 unknown、站点维护；面板只能显示一条有效 current 状态，原始观察仍可展开查看。

### P1：修正 fallback 调度和一次性证据生命周期

涉及：

- `observation/src/harvest-fallback.mjs`
- `observation/src/pt-verification.mjs`
- `observation/src/pt-reconciliation.mjs`
- `observation/scripts/harvest-fallback.mjs`
- `observation/scripts/Sync-NasShadow.ps1`

要求：

1. 对唯一注册 PT：Harvest failed/unknown/missing/pending/stale 时直接生成一个 guarded candidate，不等待 Harvest task completion。
2. 对未授权纯观测 PT：只生成 `monitor_only_unconfirmed`。对现有已授权单站 PT：保留 V1 补签；能做 reviewed passive read 的站点先只读，明确同账号当天未签到后才提交，不因 Harvest 未完成无限等待。无 reviewed passive 能力不得为去掉等待而新增盲提交，保留成熟正式流程及相应安全阻断。
3. 每个 `origin + accountKey + businessDate` 同一时刻只允许一个 passive claim。已有同一证据不得重复提交；读失败、锁忙和登录恢复分别有界退避，当前日新的恢复事件可再次只读，不得让一次早期失败卡死整日。只读失败不消耗提交次数。
4. 旧 `harvest_waiting + submissionState=not_submitted` 只在 `nextEligibleAt` 到期后唤醒一次；唤醒记录本身不是成功证据。
5. 新的 Harvest 结果、站点维护、任务完成时间变化不得把已创建的 guarded candidate 变成重复提交；执行前仍做一次当前范围和账号复核。
6. Harvest SSH 查询失败时：显示层可以保留最后一份有效缓存；有安全只读能力的已授权 PT guarded read 可继续，但不得把缓存当签到证明；未授权纯观测站点仍是 `monitor_only_unconfirmed`。
7. `newAttempts=0` 时不启动 worker；历史未知记录不得因为同步轮询反复变成新任务。

P1 验收：模拟 pending Harvest、查询超时、旧 deferred_preflight、V1 读到 not_signed、V1 读不到证据、V1 submission_unknown、signed Harvest 六种场景，检查 worker 次数和结果文件。

### P2：保留窗口修复，补齐自动路径测试

涉及：

- `execution/src/browser.mjs`
- `execution/src/offscreen-windows.mjs`
- `execution/src/oauth-login.mjs`
- `execution/src/native-oauth-login.mjs`
- `execution/scripts/Prepare-NativeWafSession.ps1`
- `execution/scripts/Invoke-MainChromeCheckinAccessibility.ps1`
- `execution/scripts/Cleanup-NativePtRead.ps1`

要求：

1. 自动任务统一使用 offscreen；手动登录入口继续 visible。
2. 主 Chrome fallback 只允许识别“本次新增、当前 Profile、启动坐标离屏”的唯一 HWND；URI 必须匹配，用户已有窗口不能被关闭或移动。
3. 窗口发现必须支持隐藏 Chrome 的 Win32 EnumWindows + UIA.FromHandle；不能只依赖桌面 UIA 子树。
4. OAuth popup 管理只作用于 headless=false/offscreen context；先注册 callback listener，再等待有界离屏定位；不改写 `window.open`、opener、postMessage 或回调导航。
5. timeout cleanup 只关闭带本次 owner token 的 HWND，并先隐藏和恢复 safe normal bounds；任何 cleanup 失败不得改变签到成功/失败语义。
6. 明确记录平台限制：popup 可能有几十毫秒创建闪现或前台切换，不能把“最终离屏”表述成“零闪现”。

P2 验收：PS5.1/PS7、冷启动、已有同 Profile Chrome、新 popup、OAuth 自关闭、主 Chrome UIA Invoke、最小化异常、未授权 HWND cleanup。

## 必须新增的回归场景

| 场景 | 预期 |
|---|---|
| Harvest 全站 unknown、taskCompletion=null | 已授权可只读 PT guarded_read_needed；纯观测 unconfirmed；保留全部补签能力 |
| Harvest signed，权威同日 | status-only already_signed；零 V1 submit |
| 注册 PT passive not_signed 同日同账号 | 只允许一次 V1 submit + 权威回读 |
| passive 无账号、跨日、缺 page signal | verification_pending/unconfirmed；零 submit |
| V1 submission_unknown | 保留审计；后续只读；零 replay |
| 纯观测 PT exact catalog unknown、无补签授权 | monitor_only_unconfirmed；不启动浏览器 |
| 已授权单站 PT exact catalog unknown、有安全只读能力 | 同账号当天先读后写；不删除单站补签能力 |
| 维护/TLS/DNS | external_blocked；不计成功率、不登录重试 |
| 旧 deferred_preflight + nextEligibleAt 未到 | 不唤醒 |
| 旧 deferred_preflight + nextEligibleAt 已到 | 只唤醒一次 |
| 主 Chrome 已有用户窗口 + 自动 fallback | 只处理本次新 HWND，用户窗口位置不变 |
| OAuth popup | 最终离屏、回调监听不丢、context 关闭无残留 |

## 执行顺序和硬门槛

6.1sol 按以下顺序执行，任何一项失败都停止发布：

1. 运行现有书签范围预检、检查 V1/V2/Harvest locks、确认 Chrome 任务进程为空闲；不修改账号和书签。
2. 先写/更新 P0/P1 fixture 和状态模型测试，再改实现；不先改真实站点规则。
3. 运行 `npm test`（execution + observation）、`npm run lint`、两层 `npm audit --omit=dev --audit-level=high`、PowerShell 解析、`Scan-PublicSafety.ps1`。
4. 用脱敏 fixture 跑 `harvest-fallback.mjs` preview，必须看到 registered candidate、monitor-only unconfirmed、external blocked 三类分离。
5. 生成 release plan，确认只包含预期文件；保护 config/config.local、Profile、账本、原始日志和运行数据。
6. 备份优先 apply；apply 后运行 release audit、V1 health、锁检查和 snapshot/generation/ledger SHA-256 对比。
7. 先做一个只读站点验收，再做一个明确 `not_signed` 的受控补签验收；已签到站点禁止提交。
8. 同步 NAS 后读取 `/healthz`、授权读取 `/api/overview`、`/api/pt-status`，确认 `snapshotMeta.generationStale=false`、业务日期正确、PT 状态与本地一致。
9. 连续观察至少两个调度周期：成功同步、Harvest 查询失败、同步超时、无新变化四种结果都要有明确 state；无变化不能重复通知或重复签到。
